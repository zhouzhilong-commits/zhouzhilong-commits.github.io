这篇用“足够工程化的直觉”理解三个问题：

- 进程/线程分别解决什么？
- 为什么会有上下文切换？
- 上下文切换的成本来自哪里？

![进程/线程/上下文切换：从“隔离”到“代价”](/images/diagrams/os-process-thread-context-switch.svg)

## 1. 进程 vs 线程：资源隔离与执行单元

- **进程（Process）**：更像“资源容器”，拥有独立的虚拟地址空间、文件描述符表等。
- **线程（Thread）**：更像“CPU 的执行单元”，共享同一进程内的大部分资源（地址空间、FD 等）。

一句话：**进程管隔离，线程管并发执行**。

## 2. 什么是上下文切换

CPU 在不同线程之间切换时，需要保存/恢复一组状态：

- 通用寄存器、程序计数器（PC）、栈指针（SP）
- 内核态相关状态（例如调度/中断相关）
- 可能还包括地址空间切换带来的 TLB 影响

这就是 **context switch**。

## 3. 什么时候会发生上下文切换（你线上看到的大多数“抖”都从这里来）

常见触发点：

- **时间片用完**：调度器把 CPU 让给其它 runnable 线程
- **线程阻塞**：等待 IO/锁/条件变量/网络 → 让出 CPU
- **优先级抢占**：更高优先级任务到来，中断当前任务
- **中断/软中断**：内核需要处理硬件事件（网络收包、磁盘完成等）

工程直觉：**上下文切换不是坏事，但“频繁且无收益的切换”会制造长尾**。

## 4. 为什么上下文切换“贵”：不是保存寄存器，而是“工作集被打散”

常见成本来源：

- **缓存污染**：新的线程工作集不同，导致 L1/L2/L3 命中率下降
- **TLB miss**：尤其跨进程切换时，地址空间变化更明显
- **内核调度开销**：队列操作、锁、统计等

很多时候“保存/恢复寄存器”的成本反而不是主角；真正伤的是：

- cache line 在不同 core 上来回热/冷
- TLB 被冲掉导致页表遍历
- 频繁切换把 CPU 变成“搬运工”而不是“干活”

## 5. 你怎么判断系统是“在干活”还是“在切换”

非常实用的观测信号：

- **context switch 频率**：异常高往往意味着大量阻塞/争用或线程过多
- **run queue（每核）**：排队长说明 CPU 紧张；排队不长但切换多，可能是频繁阻塞/唤醒
- **CPU 利用率按核分布**：平均值不可信，热点核更关键
- **P99 与切换相关性**：长尾时刻是否伴随切换飙升/softirq 飙升

## 6. 常见优化方向（按优先级）

1. **减少不必要的唤醒/阻塞**：锁竞争、条件变量“惊群”、过小任务切分
2. **控制线程数与并发度**：线程数不是越多越好，超过核数会引入调度开销
3. **提升局部性**：让相关工作尽量在同核/同线程上完成（避免工作集频繁迁移）
4. **避免热点核**：中断绑核/网络收包/后台任务把关键核打爆会制造 P99

## 7. 小结

进程提供隔离，线程提供并发；上下文切换是并发的代价。线上排障时，把“切换频率、阻塞原因、热点核”这三件事抓住，很多“明明 CPU 不高但 P99 很差”的问题就能迅速归因。
